**What exists and works.** `src/data/fitment.ts` with the six entities, the Confirmed gate

rewritten so `results` is reachable **only** on a server-confirmed `FITTED`; and the demand log.

**All 212 cars are loaded and none is Confirmed, so the site refuses every car — correctly.** The
refusal is not a gap: the alternative was answering *"100% precision-molded … in stock for your car"*
for all 4,671 car/year combinations with nothing behind any of them. **The live confirmed count is still
0**, so M2's gate assertion `>= 1` still fails, and 2.11 is why. Turning refusals into sales is now one entry
per car in `src/data/fitment-review.ts` — data entry, not code.

**Where to read the count from, and it matters.** `liveLayoutCount()` in `src/data/fitment.ts` is
**deprecated** (§6.12): it counts a compile-time table and so returns 0 forever. The real number is
`liveLayoutCountLive()` in `src/lib/fitment-live.ts`. Both are 0 today, which is exactly why the
difference is invisible until the first car is confirmed.

**The preload deserves precision, because "212 layouts loaded" could be misread as 212 claims.**
`src/data/fitment-catalogue.ts` derives one `Vehicle`, one inferred `Layout` and one inferred `Mapping`
per car from `cars.ts`, with four variants priced from `products.ts` at each brand's tier. Inferred rows
are invisible to `/fit-check` by locked decision 2, so none of it can reach a customer. What it buys: a
reviewable list, a per-car activation path, and three distinct refusals where there used to be one —
unknown car, known car outside the covered years, and known car whose floor pan nobody has confirmed.
`npm run fitment:report` prints coverage, per-make counts and the 13 `internalCode` collisions; `--ids`
lists what to paste into the review file.

**One task WAS violated rather than merely unfinished: 5.5** — the demand write was client-triggered, which
this spec forbids in as many words, and with 5.6 (`demandLogged` absent) refusals through the API were
silently uncaptured and a closed tab lost them. **Fixed 2026-10-03 and verified live**; the task line
carries the proof.

**This pass: the storefront now reads the fitment tables — §6.10–6.12, which had no task line anywhere.**
`src/lib/fitment-live.ts` adds `checkFitLive()`, `liveLayoutCountLive()` and
`confirmedCustomerNamesLive()`; `/api/fit-check` and `src/lib/demand-log.ts` call them. Before this,
confirming a layout in the admin console changed **nothing** a customer saw — the front end still read the
compile-time tables in `src/data/fitment.ts`, which are empty and permanent. §9.11 (*"so the rule holds
after the database replaces the static file"*) assumed the swap had already happened, and M9's own exit
gate requires it. Proven against Postgres rather than read: a hand-inserted confirmed Corolla layout made
`/api/fit-check` answer `FITTED` at `₦45,000`, and each of `confidence: "inferred"`, `status: "draft"`,
`priceFrom: 0` and a missing `confirmationNote` put it back to `NOT_STOCKED` — the last with HTTP 200 and a
drop log line, not a 500. All test rows were deleted and the baseline re-proved at `confirmed 0`.

**Also found while checking, and fixed because it destroys data:** the demand log defaulted to
`/tmp/luxeride-demand.ndjson`, and `/tmp` is **tmpfs** on this machine — every refusal would have been
lost to the next reboot. Moved to `~/.local/state/luxeride/demand.ndjson`.

### Operational note for anyone running an agent or a second server here

**Next 16 permits exactly one `next dev` per directory** — a second invocation aborts with *"Another next
dev server is already running"*. The shared-`.next/` hazard is therefore broader than "do not run
`next build` while someone is developing": it applies to **any** second server in this repository. The
workaround used here was to copy the app to a scratch directory, symlink `node_modules`, and pass
`--webpack` because Turbopack rejects a `node_modules` symlink pointing outside the project root. Plan
for that rather than assuming two agents can each have a dev server.

### A defect found while testing 7.1–7.5, and it is a nasty one (2026-10-03)

**The credential silently truncated, and every login failed with a 401 and no explanation.**

`scrypt$<saltHex>$<hashHex>` — the format this spec mandates — contains two dollar signs, and **Next's
env loader does shell-style variable expansion**. So `ADMIN_PASSWORD_HASH="scrypt$3055…"` was read as
`scrypt` followed by a variable named `3055…` that does not exist, and arrived in the proxy as the
six-character string `scrypt`. The verifier correctly returned false for every attempt.

Measured, same file, both loaders, side by side:

| Value in `.env.local` | Next's loader | Node's `--env-file` |
|---|---|---|
| `"a$b"` | `a` — **silently truncated** | `a$b` |
| `"a\$b"` | `a$b` | `a\$b` — backslash kept, not unescaped |

**The two loaders disagree, which is the part worth remembering.** `\$` is Next's escape for a literal
dollar, and Node does not implement it. So:

- `.env.local` must escape the dollars, and `scripts/hash-admin-password.mjs` now prints the **escaped**
  form so nobody pastes an unescaped one.
- `src/lib/admin-auth.ts` strips a stray `\$` before parsing, so the value verifies under **either**
  loader. A credential that works with `next dev` and fails under a Node script — or the reverse — is
  exactly the kind of difference nobody debugs twice.
- **The same hazard applies to every variable whose value contains a dollar sign, `DATABASE_URL`
  included.** A database password containing `$` would be expanded by the app and passed through intact
  by the Prisma CLI, so the two would disagree about which database they were talking to.

`.env.example` documents both variables and the escaping requirement, because that file is the committed
record of what the app needs.
