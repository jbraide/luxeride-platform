# Requirements Document

## Introduction

**Feature:** `fitment-engine` — the Layout grouping data model, the evidence/publish gate, the admin
console, the `/fit-check` front-end contract, the demand log and the audit trail.

This feature is the authority every other LuxeRide spec defers to on fitment. Where
`storefront-catalog`, `fit-finder`, `cart-checkout`, `commerce-backend`, `ad-landing-and-tracking`
or `trust-and-policies` have an opinion about whether something fits a car, this document wins.

**Governing source:** `luxeride-web/luxeride-fitment-engine-admin-layout-grouping-spec.md` (261 lines),
read in full. Every rule, table, edge case, phase and locked decision below is traceable to it.

**What breaks without it.** The application currently decides fitment from one boolean per
brand/model in `src/data/cars.ts` (`available`, lines 11 and 69–76). `confirmYear()` in
`src/components/FitFinder.tsx` (lines 62–69) never inspects the selected year. The results screen
then prints `FIT ✓` (`src/components/FitFinder.tsx:268`) and the sentence *"100% precision-molded …
in stock for your {year} {brand} {model}"* (lines 246–248) on the strength of nothing. The same
sentence is printed identically for a 2009 Corolla and a 2026 Corolla. There is no Layout, no
Vehicle, no Mapping, no Exclusion, no evidence gate and no demand log anywhere in the repository
(`_CONTEXT.md` §6, §11). A paid-traffic storefront whose load-bearing claim is a fabricated "yes" is
exactly the scam shape the source doc says the refusal exists to distinguish itself from (source doc
lines 129–130).

**The principle.** A car model does not have a floor pan; a **generation** does
(source doc line 7). Storing a row per model-year produces ~40 models × 6 years = **240 rows**, most
of them duplicates, each demanding its own photography — and you can photograph maybe 25 (source doc
line 15). So the unit we stock, photograph and sell is the **Layout**, and grouping is simply how many
car records become one Layout (source doc line 19).

## Requirements

### Requirement 1 — Layout-as-unit-of-sale

**User Story:** As the owner, I want images, price, notes and stock to attach to one floor pan rather
than to each model-year, so that I can photograph 25 things instead of 240 and every car inside a
group is correct by construction.

#### Acceptance Criteria

1.1 WHEN any image, price, note, lead time or stock value is set on a group of cars THEN THE SYSTEM
SHALL store it once on the parent **Layout** and read it from there for every **Vehicle** mapped onto
that Layout.

1.2 WHEN one Layout's photographs or prices change THEN THE SYSTEM SHALL reflect the change on every
Vehicle mapped onto that Layout without any per-Vehicle edit.

1.3 THE SYSTEM SHALL represent a Layout as one physical floor pan, carrying `makeId`, `bodyType`,
`driveSide` and `kind` (`footwell` | `boot`), and SHALL NOT represent a model-year as a sellable unit.

1.4 WHEN a Vehicle record is created THEN THE SYSTEM SHALL require it to resolve to exactly one Layout
via a Mapping, or to zero Layouts (unmapped), or to be recorded as an Exclusion.

1.5 THE SYSTEM SHALL NOT create or expose any product, price, image or stock record keyed on
make + model + year.

### Requirement 2 — Dual naming: internal code and customer name

**User Story:** As the owner, I want every layout to carry a short internal code for my SKUs and my
own reference in WhatsApp, and a readable customer-facing name for the site, so that a conversation
and an order can be tied together in seconds without exposing internal vocabulary to buyers.

#### Acceptance Criteria

2.1 WHEN a Layout is created THEN THE SYSTEM SHALL assign it an **internal code** in the form
`<MAKE-TICKER>-<yearFrom>-<yearTo>`, for example `TC-2009-2013`, used in the admin console, in SKUs
and in references.

2.2 WHEN a Layout is created THEN THE SYSTEM SHALL assign it a **customer name**, for example
`Toyota Corolla 2009–2013`, used on the front end and in the prefilled WhatsApp message body.

2.3 THE SYSTEM SHALL render the internal code **nowhere** in the customer-facing UI — not as a badge,
not as a heading, not as a caption, not in page copy.

2.4 WHEN a WhatsApp link is generated by `/fit-check` THEN THE SYSTEM SHALL embed the internal code
inside the prefilled message text as `(ref TC-2009-2013)`, so the reference appears in the customer's
own WhatsApp composer and in the resulting chat with the owner.

2.5 THE SYSTEM SHALL treat an internal code as immutable once it has been published. Changing a
Layout's identity SHALL require retiring the Layout and creating a new one, because codes already
quoted to customers must keep resolving.

2.6 THE SYSTEM SHALL reject a Layout whose internal code is not unique, and SHALL reject a code that
does not match `^[A-Z0-9]{2,3}-\d{4}-\d{4}$`.

2.7 WHEN a Layout's customer name is derived from a grouped selection THEN THE SYSTEM SHALL derive it
from the **widest** year span in the selection and SHALL allow the owner to override it before save.

### Requirement 3 — The six entities and their fields

**User Story:** As the owner, I want fitment truth stored as six clearly separated entities, so that
a car name, a floor pan, the join between them, what is sold, what it looks like, and what it does not
fit are never confused with one another.

#### Acceptance Criteria

3.1 **Layout** — the published unit, one real floor pan. Fields: `layoutId`, `internalCode`,
`customerName`, `makeId` (required, singular), `bodyType`, `driveSide`, `kind`, `status`, `notes`,
`leadTime`. Images attach here.

3.2 **Vehicle** — a name a customer would actually type. Fields: `vehicleId`, `make`, `model`,
`yearFrom`, `yearTo`, `generation`, `aliases`, `bodyType`, `facelift`. Images do not attach here.

3.3 **Mapping** — the join. Fields: `layoutId`, `vehicleId`, `confidence`, `evidenceNote`,
`confirmedBy`, `date`. Images do not attach here.

3.4 **LayoutVariant** — what is actually sold for that Layout. Fields: `layoutId`, `productSlug`,
`kind` (`single_layer` | `double_layer` | `boot_liner` | `full_set`), `priceFrom`, `stockState`,
`rowsSurcharge`. Images do not attach here. (The source doc names this entity "Variant" in its
data-model table, line 40, and "LayoutVariant" in its field-additions table, line 255. They are the
same entity; this spec standardises on `LayoutVariant`.)

3.5 **ImageSet** — the photographs for that Layout, one per angle. Fields: `layoutId`, `angle`
(`driver` | `passenger` | `rear` | `boot` | `detail` | `comparison`), `src`, `alt`, `capturedOn`,
`supersededAt`. Images attach here.

3.6 **Exclusion** — looks like it belongs, does not fit. Fields: `vehicleId` or `vehicleId + trim`,
`layoutId` (the Layout it was wrongly assumed to fit), `reason`. Images do not attach here.

3.7 THE SYSTEM SHALL reject a `LayoutVariant` of kind `boot_liner` on a Layout whose `kind` is
`footwell`, because boot ≠ footwell and a boot liner needs its own Layout mapping rather than a
variant of the footwell one (source doc line 157).

3.8 THE SYSTEM SHALL require every Entity to be created with a unique identifier that does not change
when any human-readable field is edited.

### Requirement 4 — The evidence gate and the status lifecycle

**User Story:** As the owner, I want nothing to reach the front end without physical, written or
OEM evidence, so that a "yes" is worth something and the refusal stays credible.

#### Acceptance Criteria

4.1 A Layout SHALL be allowed to reach status `confirmed` only when one of these is true:
(a) a physically confirmed fitting, (b) a written supplier confirmation, or (c) a verified OEM
floor-pan match.

4.2 WHEN a Layout is marked `confirmed` THEN THE SYSTEM SHALL require a non-empty `evidence` value
from exactly the set `physical-fitting | supplier-confirmation | oem-floor-pan`, a non-empty
`confirmationNote`, and a `confirmedOn` date.

4.3 WHEN a Layout's status is anything other than `confirmed` — `draft`, `inferred` or `retired` —
THEN THE SYSTEM SHALL treat it as invisible to `/fit-check`.

4.4 THE SYSTEM SHALL represent the status lifecycle as exactly four states:
`draft → inferred → confirmed → retired`.

4.5 WHEN a Layout moves `confirmed → retired` THEN THE SYSTEM SHALL retain the Layout and all of its
history for historical orders and SHALL exclude it from every front-end query.

4.6 WHEN a Layout is missing a required field for its current status — for example `confirmed` with
no `confirmationNote` — THEN THE SYSTEM SHALL refuse to load the fitment data rather than serve it,
so the defect surfaces at build time instead of to a customer.

4.7 THE SYSTEM SHALL keep `inferred` and `untested` reasoning distinct in the admin console, with
`untested` rendered as `draft` on the front end because neither may be shown to a customer.

### Requirement 5 — The six admin MVP screens

**User Story:** As the owner working alone, I want six screens that between them cover every change I
need to make, so that the admin is a single-operator tool rather than a system.

#### Acceptance Criteria

5.1 **Vehicles list** — filterable by unmapped / mapped / excluded, showing counts for each. The
unmapped count is the working queue.

5.2 **Grouping view** — multi-select vehicles, then create a Layout from the selection or split an
existing Layout.

5.3 **Layout detail** — images per angle, variants with prices, mapped vehicles, confidence, and the
publish toggle.

5.4 **Exclusions** — the known non-fits with their reasons, editable and removable.

5.5 **Demand log** — not-stocked requests ranked by volume.

5.6 **Audit log** — who changed what, when, and what changed.

5.7 WHEN any of the six screens is opened without an authenticated admin session THEN THE SYSTEM
SHALL deny the request and SHALL NOT render any layout, price, mapping or demand data.

---

### Requirement 6 — Grouping, the conflict guard, and split-as-a-first-class-action

**User Story:** As the owner, I want the system to stop me merging cars that are already committed
somewhere else, and to let me split a group cleanly the day I discover it was wrong, so that a bad fit
never ships because of a mis-click.

#### Acceptance Criteria

6.1 WHEN two or more selected Vehicles already sit on **different** Layouts with status `confirmed`
or `inferred` THEN THE SYSTEM SHALL refuse the merge, name every conflicting Layout by internal code,
and require an explicit Split Layout action instead.

6.2 THE SYSTEM SHALL NEVER silently merge Vehicles that are already on different non-draft Layouts.

6.3 WHEN the owner creates a Layout from a selection THEN THE SYSTEM SHALL propose a customer name
from the widest span in the selection.

6.4 WHEN a created Layout's selected Vehicles span more than one non-empty `generation` value THEN THE
SYSTEM SHALL warn and require an explicit human acknowledgement with a written reason before saving.

6.5 WHEN two selected Vehicles share make + model + generation but differ in `bodyType` THEN THE
SYSTEM SHALL refuse the grouping unless the owner flags it as verified.

6.6 **Split Layout SHALL be a first-class admin action**, exposed alongside create, not a
workaround, so a Layout can be divided without disturbing the rest of the group.

6.7 WHEN a Layout is split THEN THE SYSTEM SHALL create the new child Layout with status `draft`, so
that a newly asserted span is never published on the parent's evidence.

6.8 WHEN a Layout is split THEN THE SYSTEM SHALL record, in the audit log, the parent internal code,
the child internal code, and the exact set of Vehicles moved.

### Requirement 7 — Edge cases

**User Story:** As the owner, I want the system to encode the awkward real-world cases rather than
letting them become wrong fits, so that the refusal stays trustworthy in the cases buyers actually
argue about.

#### Acceptance Criteria

7.1 **Facelift inside a generation** — usually the same floor pan, sometimes not. THE SYSTEM SHALL
support a separate Vehicle row for the facelift mapped onto the same Layout, flagged, rather than
forcing a choice at the Vehicle level.

7.2 **Same name, different generation** — "Corolla 2013" and "Corolla 2014" are different cars.
THE SYSTEM SHALL NEVER allow a year span to cross a generation line without a human check, and
SHALL refuse to place two Vehicles of the same make + model with overlapping year ranges onto one
Layout.

7.3 **Tokunbo / used imports** — often RHD or EU/US spec; the mat is usually the same but the drive
side SHALL be recorded on the Layout regardless.

7.4 **Trim differences** — hybrid battery, 3rd row, 7-seat vs 5-seat can change the floor. THE SYSTEM
SHALL support a trim-scoped Exclusion so a known non-fit is recorded rather than guessed at.

7.5 **Boot liners** — boot ≠ footwell. THE SYSTEM SHALL require a boot liner to be mapped to its own
`kind: "boot"` Layout and SHALL NOT offer it as a variant of the footwell Layout.

7.6 **Body variants** — wagon / hatch / sedan often differ. THE SYSTEM SHALL require separate Layouts
unless the difference has been verified and flagged.

7.7 **Same platform, different brand** — rare, never assume. THE SYSTEM SHALL require verification
before any grouping spans makes, and a verified cross-brand platform match SHALL be recorded as two
cross-referenced Layouts, never one merged entity.

7.8 WHEN a Vehicle has aliases or an alternative spelling THEN THE SYSTEM SHALL match any of them
during a `/fit-check` lookup.

### Requirement 8 — The `/fit-check` contract

**User Story:** As a customer, I want to type what I drive and get a straight answer, so that I know
within seconds whether LuxeRide has my car.

#### Acceptance Criteria

8.1 THE SYSTEM SHALL expose a `POST` fit-check endpoint accepting `{ make, model, year }`.

8.2 WHEN the Vehicle is recognised and maps to a Layout with status `confirmed` THEN THE SYSTEM SHALL
return state `FITTED` containing the Layout's customer name, its LayoutVariants with `priceFrom`,
its ImageSet, its `leadTime`, and a WhatsApp link carrying the internal code.

8.3 WHEN the make and model are recognised but no `confirmed` Layout exists for that Vehicle THEN THE
SYSTEM SHALL return state `NOT STOCKED` — an honest "we don't have it yet" — together with
confirmation that a demand-log capture was made for this request and an optional waitlist capture.

8.4 WHEN nothing in the request matches any known make, model or year THEN THE SYSTEM SHALL return
state `UNKNOWN` and route the visitor straight to WhatsApp so a human answers.

8.5 THE SYSTEM SHALL return **exactly one** of `FITTED`, `NOT STOCKED`, `UNKNOWN` and SHALL NOT invent
a fourth outcome.

8.6 WHEN the lookup runs against data that fails to load, or the request cannot be satisfied THEN THE
SYSTEM SHALL return `UNKNOWN`. It SHALL NEVER fall back to `FITTED`.

8.7 WHEN the request omits `make`, `model` or `year`, or supplies a non-numeric year, or supplies a
payload over 2 KB THEN THE SYSTEM SHALL return `UNKNOWN` with a validation reason and SHALL NOT write
a demand-log entry.

8.8 WHEN a `/fit-check` is answered for a Vehicle whose mapping confidence is below `confirmed` THEN
THE SYSTEM SHALL return `NOT STOCKED`, not `FITTED`.

8.9 WHEN the visitor uses a Vehicle alias or an alternative spelling THEN THE SYSTEM SHALL resolve it
to the same Layout as the canonical name.

8.10 THE SYSTEM SHALL record every `NOT STOCKED` and `UNKNOWN` outcome as a demand-log entry.

### Requirement 9 — All three states carry a WhatsApp link carrying the ref

**User Story:** As the owner, I want every fit-check outcome — yes, no, and don't-know — to end in a
prefilled WhatsApp message that names the car and carries the reference, so that no enquiry has to be
answered from memory.

#### Acceptance Criteria

9.1 WHEN `/fit-check` returns `FITTED`, `NOT STOCKED` or `UNKNOWN` THEN THE SYSTEM SHALL include a
fully formed `whatsappUrl` in the response.

9.2 WHEN the message is for a `FITTED` outcome THEN THE SYSTEM SHALL embed the internal code as a ref,
for example: *"Hi, I drive a 2012 Toyota Corolla. Is the black TPE set available? (ref TC-2009-2013)"*.

9.3 WHEN the message is for a `NOT STOCKED` or `UNKNOWN` outcome THEN THE SYSTEM SHALL still name the
car the visitor typed and SHALL still carry whatever reference is available (the make ticker and year
range when a Layout exists but is not confirmed; nothing but the car name when nothing is known).

9.4 WHEN a `wa.me` URL is built THEN THE SYSTEM SHALL route it through the existing
`whatsappLink()` helper in `src/lib/whatsapp.ts` so the number
(`WHATSAPP_NUMBER = "2347049621694"`, `src/data/locations.ts:14`) stays in one place.

9.5 THE SYSTEM SHALL include the ref in the **message text**, not as a separate response field the UI
might choose to display, so that a customer never sees the code as site chrome.

---

### Requirement 10 — The refusal path is the product's actual job

**User Story:** As the owner, I want saying no to be cheap and instant, so that the refusal holds up
without me personally knowing every car in Nigeria.

#### Acceptance Criteria

10.1 WHEN the system refuses a fit THEN THE SYSTEM SHALL produce the refusal from stored data alone,
with no human lookup and no personal knowledge of the model.

10.2 THE SYSTEM SHALL write refusal copy to the same standard as the site's headlines — it is
first-class front-end copy, not a fallback string, because the refusal is the load-bearing claim of
the brand.

10.3 WHEN refusal copy promises future stock THEN THE SYSTEM SHALL present a waitlist capture on the
same screen. A refusal that promises stock and captures nothing SHALL NOT be published.

10.4 THE SYSTEM SHALL distinguish `NOT STOCKED` from `UNKNOWN` in the copy: "we know the car, we do
not have the floor pan" versus "we could not recognise that car at all".

10.5 WHEN a refusal copy is rendered THEN THE SYSTEM SHALL NOT use the word "soon", a date, or any
other future-stock promise unless the waitlist capture is present on that screen.

10.6 WHEN the refusal screen renders THEN THE SYSTEM SHALL reuse the existing
`comingSoonMessage(what, phone?)` helper (`src/lib/whatsapp.ts:42`) so that the waitlist entry lands in
the owner's WhatsApp inbox, which is the only waitlist store that exists before any database.

10.7 THE SYSTEM SHALL carry the Fit Guarantee language that already exists in
`src/components/FitFinder.tsx:280` onto every `FITTED` outcome and SHALL NOT attach it to a refusal.

---

### Requirement 11 — Refusals are a ranked sourcing asset

**User Story:** As the owner, I want every refusal captured and ranked, so that the models people ask
for that I do not carry become a sourcing roadmap built out of honest answers rather than guesswork.

#### Acceptance Criteria

11.1 WHEN `/fit-check` returns `NOT STOCKED` or `UNKNOWN` THEN THE SYSTEM SHALL capture the `make`,
`model`, `year`, `askedAt` and `source` of the request.

11.2 THE SYSTEM SHALL aggregate repeated requests for the same make + model into a single demand-log
row carrying a count, so the list ranks by volume.

11.3 THE SYSTEM SHALL present the demand log ranked by volume, so the most-requested unstocked model is
the first row.

11.4 **The demand log SHALL work from day one, including in Phase 0, before any admin or database
exists.** Capturing a refusal SHALL NOT depend on the P1 admin or the `commerce-backend` database.

11.5 WHEN a visitor is anonymous (no account, no email, no session) THEN THE SYSTEM SHALL still
capture the refusal, using the WhatsApp prefilled message as the owner's copy and a server-side
structured log line as the machine copy.

11.6 WHEN the demand-log write fails, times out, or is blocked THEN THE SYSTEM SHALL still render the
refusal and the WhatsApp link to the visitor. A broken demand log SHALL NOT turn a refusal into an
error page.

11.7 THE SYSTEM SHALL carry campaign attribution through to the demand-log entry from whatever
first-party attribution `ad-landing-and-tracking` captures, and SHALL NOT define its own UTM taxonomy.

### Requirement 12 — The audit log and amendment history

**User Story:** As the only person who will ever edit this data, I want every change recorded in my
own words, so that a mistake is obvious to me a week later.

#### Acceptance Criteria

12.1 WHEN a Layout, Mapping, LayoutVariant, ImageSet or Exclusion is created, edited, split, merged,
published, unpublished or retired THEN THE SYSTEM SHALL write an audit entry recording what changed,
when, and by whom.

12.2 WHEN a status change to `confirmed` is recorded THEN THE SYSTEM SHALL store the owner's
`confirmationNote` verbatim in the audit entry alongside the `confirmedOn` date.

12.3 THE SYSTEM SHALL make the audit log append-only. Entries SHALL NOT be editable or deletable from
the admin console.

12.4 WHEN a published Layout's fitment meaning changes — its status, its mapped Vehicles, or its make —
THE SYSTEM SHALL create a new revision of that Layout rather than mutating the existing revision.

12.5 WHEN only a price, note, lead time or image changes on a published Layout THEN THE SYSTEM SHALL
update in place and record an audit entry, because the entire value of grouping is that the change
reaches every mapped car at once.

12.6 WHEN an ImageSet entry is replaced THEN THE SYSTEM SHALL retain the superseded asset with a
`supersededAt` timestamp, so what a customer saw at order time can be recovered.

12.7 WHEN an order was placed against a Layout that is later split or retired THEN THE SYSTEM SHALL
leave the order's recorded fitment snapshot unchanged, so history is never rewritten.

12.8 THE SYSTEM SHALL record on every order snapshot enough to service that order without the admin
console: the internal code, the customer name, the quoted `priceFrom`, the evidence source and the
`confirmedOn` date.

### Requirement 13 — Phasing

**User Story:** As the owner, I want the fitment truth built in the cheapest order that keeps it true,
so that I can start answering in WhatsApp today without writing software first.

#### Acceptance Criteria

13.1 The build SHALL follow the six-phase ladder below.

| Phase | What | Why it sits here |
| --- | --- | --- |
| **Phase 0** | Master sheet — one row per Layout, columns of model-years, a `priceFrom` per variant | **Zero build.** In WhatsApp this is already enough to answer enquiries and hold the refusal. Start here today. |
| **Phase 1** | Admin CRUD + grouping + publish | Internal only. Replaces the sheet. |
| **Phase 2** | `/fit-check` wired to the lookup + WhatsApp ref | First customer-facing use. |
| **Phase 3** | Image manager + versioning | Change one Layout → every car in it updates. |
| **Phase 4** | Demand-log analytics — ranked unstocked models | Turns refusals into a sourcing roadmap. |
| **Phase 5** | Supplier catalogue import | Scale, once the model is proven. |

13.2 THE SYSTEM SHALL build the Phase 0 sheet and the Phase 2 front-end contract against the **same**
data representation, so that the admin replacing the sheet in Phase 1 does not change the front-end
contract and today's work is not thrown away.

13.3 THE SYSTEM SHALL NOT require a database, an admin console or an authenticated user in Phase 0.

### Requirement 14 — LOCKED DECISION 1 (Fri 2 Oct 2026): owner only, single admin

**User Story:** As the owner, I want the admin built as a single-operator tool, so that I am not
paying for permission complexity I do not have users for.

#### Acceptance Criteria

14.1 THE SYSTEM SHALL implement the admin for exactly one operator and SHALL NOT build roles,
permissions, a permission matrix, an audit-of-editors, or a second editor seat.

14.2 **Consequence, binding:** with one editor, a fat-fingered status change is the whole risk, so
transitioning a Layout to `confirmed` SHALL require a mandatory short `confirmationNote` and SHALL
record `confirmedOn`. These are required fields, not optional process.

14.3 THE SYSTEM SHALL render `confirmationNote` and `confirmedOn` on the Layout detail screen and on
the audit log entry, so a mistake is legible to the owner later without opening the console's history.

14.4 WHEN a session method is chosen for the admin THEN THE SYSTEM SHALL still gate every mutating
server action server-side. Render-time gating alone is not a security boundary, because a Server
Action is a POST endpoint reachable by anyone who can send the same request.

### Requirement 15 — LOCKED DECISION 2 (Fri 2 Oct 2026): Confirmed only on the front end

**User Story:** As the owner, I would rather refuse ten cars than answer one wrongly, so that the
"we say no" promise survives contact with a customer.

#### Acceptance Criteria

15.1 THE SYSTEM SHALL return `FITTED` only for a Layout with status `confirmed`. `inferred` and
`draft` Layouts SHALL be invisible to `/fit-check`.

15.2 **Consequence, binding:** at go-live the Confirmed Layout count will be small, so `/fit-check`
SHALL refuse more cars than it accepts. That is the intended, honest behaviour and SHALL NOT be
worked around by loosening the gate.

15.3 **Consequence, binding:** the demand log SHALL work from day one, including in Phase 0, because
every refusal is the asset and refusals that are not captured lose the only sourcing signal the site
generates.

15.4 **Consequence, binding:** refusal copy SHALL be treated as first-class front-end copy written to
headline standard, and SHALL carry a waitlist capture whenever it promises future stock.

15.5 **Consequence, binding:** the system SHALL make the list of Confirmed customer names derivable
without a database, so `ad-landing-and-tracking` can align ad copy to cars the site will actually
accept, and can refuse to run creative naming a car `/fit-check` will refuse.

15.6 **Consequence, binding:** broad ad targeting into a mostly-refusing `/fit-check` is a
demand-mapping exercise, not an acquisition exercise, and the coordination between them SHALL be
recorded with `ad-landing-and-tracking` before spend.

15.7 **Consequence, binding:** the Confirmed Layout count at launch SHALL be computable from the
fitment data with a single function call and SHALL be written down on go-live day as a launch metric.

---

### Requirement 16 — LOCKED DECISION 3 (Fri 2 Oct 2026): price on the site

**User Story:** As the owner, I want the site to show a price, so that buyers who expect one do not
treat its absence as evasion.

#### Acceptance Criteria

16.1 THE SYSTEM SHALL display a price on the front end, attached to the **LayoutVariant** as
`priceFrom`, not attached to the car and not attached to the product catalogue alone.

16.2 THE SYSTEM SHALL carry a `priceFrom` per variant on the Phase 0 master sheet, not later.

16.3 THE SYSTEM SHALL render the price as a range or a "from" figure whenever the exact figure varies
by model, and SHALL NEVER display a single exact figure that the subsequent WhatsApp quote
contradicts. A site price the quote overrides is worse than no price.

16.4 **Counter to the "price last" asset hierarchy, explicitly.** The proof → risk-removal → price-last
hierarchy governs **cold ad creative**. It does **not** govern the site, where price is expected. The
site rule SHALL NOT leak backwards into Stage 1–3 creative, where naming price early still costs the
scroll.

16.5 WHEN a `FITTED` result is rendered THEN THE SYSTEM SHALL price from the LayoutVariant the visitor
selected, and SHALL NOT compute the price from the brand tier, in place of or alongside the layout
price.

16.6 WHEN a Confirmed Layout has no `priceFrom` on a variant the visitor would be offered THEN THE
SYSTEM SHALL NOT return `FITTED`, and SHALL return `NOT STOCKED` instead, rather than showing a
fallback catalogue price — because a wrong price on a confirmed fit is worse than an honest refusal.

### Requirement 17 — LOCKED DECISION 4 (Fri 2 Oct 2026): one layout = one make

**User Story:** As the owner, I want each Layout to belong to exactly one make, so that grouping stays
simple and Split Layout stays meaningful.

#### Acceptance Criteria

17.1 THE SYSTEM SHALL require a single, non-null `makeId` on every Layout.

17.2 WHEN any grouping operation would place Vehicles of two different makes onto one Layout THEN THE
SYSTEM SHALL refuse it.

17.3 WHEN a genuine cross-brand platform match is confirmed THEN THE SYSTEM SHALL record it as **two
Layouts with two rows, cross-referenced in the notes field**, and SHALL NOT create one merged entity.

17.4 THE SYSTEM SHALL never assume cross-brand platform sharing; it requires verification first.

---

### Requirement 18 — ImageSets per Layout, per angle

**User Story:** As the owner, I want photographs attached to the floor pan rather than to the product,
so that changing one car's photos updates every model mapped onto it.

#### Acceptance Criteria

18.1 THE SYSTEM SHALL store images per Layout per angle, with the six angles `driver`, `passenger`,
`rear`, `boot`, `detail` and `comparison`.

18.2 WHEN a `FITTED` result is rendered THEN THE SYSTEM SHALL show the **ImageSet** of the matched
Layout, not the generic `Product.images` array, because the claim being made is about this specific
car.

18.3 THE SYSTEM SHALL keep `Product.images` (`src/data/products.ts:12`) as the catalogue-level image
list for `/shop` and `/products/[slug]`, which is a different axis: what the product is, versus how it
sits in this car.

18.4 WHEN a Layout has no asset for an angle THEN THE SYSTEM SHALL omit that slot without rendering a
broken frame, and SHALL NOT let the absence of photographs suppress the fit result or its price.

18.5 WHEN a `FITTED` result has no images at all THEN THE SYSTEM SHALL present the "ask us for live
photos" affordance, which already exists in `src/components/FitFinder.tsx:306-315`, in place of an
empty image strip.

18.6 WHEN a `kind: "boot"` Layout is photographed THEN THE SYSTEM SHALL require the `boot` angle and
SHALL NOT require the footwell angles; a `kind: "footwell"` Layout is the mirror image.

18.7 WHEN an image is added to the admin THEN THE SYSTEM SHALL set a real `alt` text. The existing
galleries render `alt=""` in both the PDP strip and the fit-result strip, and on a fit-claim page the
alt text is both an accessibility obligation and free keyword surface.

### Requirement 19 — Reconciliation with what exists today

**User Story:** As the owner, I want the new fitment model to supersede today's ad-hoc availability
flags without breaking the storefront that already works, so that I get the truth without losing the
catalogue.

#### Acceptance Criteria

19.1 THE SYSTEM SHALL supersede `Car` (`prisma/schema.prisma:36-46`) with `Vehicle` + `Layout` +
`Mapping`, and supersede `CarModelFlag` (`prisma/schema.prisma:48-53`), which is an ad-hoc
single-model availability hack with no place in a fitment model.

19.2 WHEN today's `available: false` is interpreted under this spec THEN THE SYSTEM SHALL treat it as
`NOT STOCKED` — a recognised make with no Layout — because that is precisely what it has always meant
to the customer.

19.3 WHEN today's `available: true` is interpreted under this spec THEN THE SYSTEM SHALL NOT carry
that flag into the fit-check. Most of it becomes `NOT STOCKED` at launch, because a flag that was never
backed by a fitting is not evidence.

19.4 THE SYSTEM SHALL keep `Brand.tier` (`src/data/cars.ts:12`) as a catalogue browsing input only.
It SHALL NOT be an input to a fitment price, because price attaches to the LayoutVariant.

19.5 THE SYSTEM SHALL keep `Product.regular` / `premium` / `threeRowSurcharge`
(`src/data/products.ts:9-10`) as the catalogue's browsing prices and SHALL treat
`LayoutVariant.priceFrom` as authoritative for anything sold after a `FITTED` result.

19.6 THE SYSTEM SHALL reconcile the fitment spec's Variant vocabulary (`single layer`, `double layer`,
`boot liner`, `full set`) with the seven catalogue `PRODUCTS` by keying every LayoutVariant to a
catalogue product slug, so that the two lists cannot drift apart.

19.7 THE SYSTEM SHALL deliver its database models through `commerce-backend`, which owns migration
staging, and SHALL keep the fitment migration **additive** — new tables plus new nullable columns —
so the still-static storefront is never blocked by a fitment migration.

19.8 THE SYSTEM SHALL NOT require the Prisma schema, `@prisma/client`, a `prisma/migrations/`
directory or any database connection in Phase 0.

### Requirement 20 — What happens to orders when a Layout is split or retired

**User Story:** As the owner, I want an order placed against a correct fit to stay correct on paper
even after I later split or retire the Layout it was placed against, so that a price or mapping change
never rewrites history.

#### Acceptance Criteria

20.1 WHEN an order line is created from a `FITTED` result THEN THE SYSTEM SHALL snapshot onto that
line the Layout's internal code, customer name, quoted `priceFrom`, evidence source and `confirmedOn`
date, alongside the existing `unitPrice` and `rows` snapshot on `OrderItem`
(`prisma/schema.prisma:80-93`).

20.2 WHEN a Layout is split or retired after the fact THEN THE SYSTEM SHALL NOT rewrite, delete or
re-point any historical `OrderItem` snapshot.

20.3 WHEN a Layout is split THEN THE SYSTEM SHALL set `supersededByLayoutId` on the parent and record
the split in the audit log, so the old Layout remains resolvable by its internal code for anyone
holding an old WhatsApp ref.

20.4 WHEN a customer holding an old ref asks about an order placed before a split THEN THE SYSTEM
SHALL be able to answer entirely from the order snapshot without opening the admin console.

20.5 WHEN the quote a customer accepted differs from a later published price THEN THE SYSTEM SHALL
honour the snapshot price for that order, because the site showed them that number.
